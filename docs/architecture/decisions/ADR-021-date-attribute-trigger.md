# ADR-021: A date-attribute journey runs once per local day and enrolls each customer once per occurrence

- **Status:** Accepted (2026-11-21, WP-25)
- **Context:** A florist's best message is one a week before a customer's anniversary or birthday. The journey definition already named a `date_attribute` trigger (ADR-011), but nothing started it. The risks are the ones of the segment schedule (ADR-013): a customer enrolled twice for one occasion, a day run twice by two workers, a backlog of old reminders sent after downtime, and a message at the wrong hour of the tenant's day. A new one: the occasion comes back every year, so "once" must mean once per occurrence, not once ever.
- **Decision:**
  1. **What the trigger means.** `date_attribute {attribute, offset_days, at_local_time}`. The attribute holds a date, `YYYY-MM-DD` alone or at the start of an ISO timestamp (what the CSV import stores for any extra column). The occasion is the **month and day**; the year recorded does not matter. The journey fires on `occasion day + offset_days` at `at_local_time` in the tenant's time zone: `-7` is a week before, `0` on the day, `3` three days after.
  2. **One run per local day** (`engage.date_runs`, migration 133). A run is claimed with one row per (journey, local day), in chunks that each lock the run row and move a keyset cursor, exactly as a segment run (ADR-013 decision 5): counts add up, an interrupted run resumes after ten minutes, a finished run cannot change, the engage role cannot delete one. It enrolls every customer whose occasion falls on `run day - offset_days`. Only the latest due day runs: after downtime, missed days are **not** made up, because a reminder that arrives after its day is worse than none. The first run is the first scheduled moment after activation, never at once. One run enrolls at most 100,000 customers (`truncated` says so).
  3. **Once per occurrence.** The enrollment key is `date:<occasion day>:<customer>` (trigger kind `date`), unique per journey, so retries, repeated runs and concurrent workers cannot enroll a customer twice for one occurrence, and next year's occurrence is a different key. The journey's re-entry rule still applies, so the definition **must** use `re_entry: after_exit` (a `never` journey would refuse the second year's occasion without a word; the definition is refused instead). A customer still in the journey when the next occasion comes is skipped and counted as skipped.
  4. **29 February** is celebrated on 28 February in a year without one: on that day customers recorded as 02-29 match as well as those recorded as 02-28. In a leap year it is the 29th, and the 28th does not match them.
  5. **Matched as text, never cast.** The attribute value is compared as characters (`^\d{4}-\d{2}-\d{2}` then the month and day), never converted to a date, so a malformed value (`2023-13-45`, `12/03/2020`, a number, an array, a leading space) cannot raise an error or stop the run: it simply does not match. Erased customers never match. The attribute name is a bound parameter.
  6. **The sends are unchanged.** The audience is "has the date", not "has consent". Consent, suppression, quiet hours, frequency cap, budget and the sandbox allow-list are applied by the send gate to every message, as for any journey; a marketing reminder to a customer without email consent is blocked there, not here.
  7. **Work across tenants.** `engage.due_date_work(orgs)`, a fourth id-only SECURITY DEFINER list (reviewed in the isolation suite), names the active date-triggered journeys. The tick runs due date runs after the segment runs and before the due enrollments; the scheduled tick and the tenant tick both do it, and the tenant filter of migration 123 applies. The tick summaries gain `dateRuns`.
  8. **The ready-made journey** (`engage/journeys/occasionReminder.ts`): one marketing reminder email from the template `occasion-reminder` (Turkish, no claim about stock, price or delivery), then the end, holdout 10% (D-11). `installOccasionReminder` creates the template and a **draft** journey `occasion-<attribute>` and never approves or activates (ADR-011). Operators install it with `npm run engage:install-occasion`.
  9. **API:** `GET /api/engage/journeys/:id/date-runs` lists a journey's runs (tenant users). The journey form on the Lucy page does not create date-attribute journeys yet.
- **Consequences:** + a whole year of daily runs enrolls every customer with a valid date exactly once (tested over 365 daily runs, with leap days, garbage values, erased customers and a second year); + the schedule survives retries, two workers and downtime without a duplicate or a late backlog. − a customer with two occasions needs two journeys (one per attribute); − the occasion is a calendar date, so an event that moves (a wedding on a specific day, Mother's Day) is not covered: that is a segment or a one-off campaign; − a tenant time zone change takes effect from the next run (the zone is read at each run), and daylight-saving transitions are left to the database's zone rules, which are not tested here (Turkey, the first market, has none); − a missed day's customers get nothing for that year (by design, see 2); − no UI to create the journey yet.
- **Not in v1:** the journey form for this trigger, several attributes in one journey, recurring non-annual dates (every 6 months), "next order" dates such as a repeat purchase interval, and a date attribute written by events instead of imports.
