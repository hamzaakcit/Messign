# ADR-025: WhatsApp templates are registered in Messign, mirrored from Meta, and judged by the send gate before anything is sent

- **Status:** Accepted (2026-11-23, WP-40a), extended by WP-40b (journeys, campaigns, segments, consent capture) and WP-40c (Settings, ops alerts; addenda below). The live check with a Meta test number follows WP-40c's merge.
- **Context:** WP-27 (ADR-023) made sending a WhatsApp template possible, but nothing in the product could use it: there was no WhatsApp template in Messign, no way to know whether Meta had approved, paused or recategorized one, and nothing stopped a large campaign from running into Meta's limit on how many customers a business may contact in a day. Built from Meta's official documentation (developers.facebook.com, WhatsApp Business Platform, read 2026-11-23: message templates, template components, the template status webhook, messaging limits, throughput, permissions, error codes). The plan is `docs/roadmap/wp-40-whatsapp-plan.md`.
- **Decision:**
  1. **Templates are written and approved at Meta; Messign registers how to fill them.** A WhatsApp template keeps its key and name in `engage.templates` (channel `whatsapp`, migration 137), so a journey refers to it like any template. Its versions (`engage.whatsapp_template_versions`, append-only) hold the Meta name and language, the approved body text, the declared category (marketing or utility), how a customer can stop (`quick_reply`, `text_in_body`, `none`), and where each numbered variable comes from: a customer attribute, a trigger value, or the tenant's sender name, with an optional default. Optionally one text-header variable and one URL-button variable (appended to the button's base URL). Named variables, media headers, authentication templates and other button kinds are refused or reported as unsupported. Messign does not create or submit templates at Meta (a later decision: it changes what Messign is responsible for).
  2. **Rendering is pure** (`whatsapp/render.ts`): values from those three places only (R-5), cleaned the way Meta wants parameters (line breaks, tabs and runs of spaces collapsed; Meta's documentation does not list the characters, so this is deliberately conservative), never cut. A missing value without a default, or a value that is too long, fails the render; the message is recorded with the reason and the gate denies it (`render_<code>`), as for email. URL-button values are percent-encoded.
  3. **Meta's word is mirrored per tenant** (`engage.whatsapp_template_status`, RLS; history in `engage.whatsapp_template_events`, append-only, one row per change, idempotent on Meta's event). Two writers: the **template check** (`GET /<WABA id>/message_templates`, all pages, needs the account's `waba_id` config; hourly job `engage/whatsapp-template-check` for tenants whose last attempt is over 55 minutes old, found by `engage.whatsapp_sync_work`, ids only; and on demand, `POST /api/engage/whatsapp/templates/check`) and **Meta's `message_template_status_update` webhook** on the account's existing URL (signed like every delivery; read only for the account's own WhatsApp Business Account; an update older than what the mirror holds is recorded, not applied; `REINSTATED` means approved, `FLAGGED` only lowers the quality, `UNARCHIVED` and unknown events wait for the next check). A complete listing marks a template Meta no longer lists as `DELETED`. A failed check changes no status and records a code (`wa_190`, `waba_missing`, ...), never Meta's text.
  4. **The send gate judges every WhatsApp template message against the mirror**, from the values the message itself carries (so a hand-built message is judged the same way):
     - `template_not_approved`: Meta's status is anything but APPROVED (pending, rejected, paused, disabled, deleted, ...).
     - `template_status_unknown`: never seen at Meta. Denied in **live** mode; allowed in sandbox, where a Meta test number's sample templates may not be registered.
     - `template_mapping_mismatch` (with the problems): the number of body, header or button values does not fit the shape Meta reports, or the template has a header or button Messign cannot fill. Meta would refuse it (wa_132000 and friends); now nothing is sent.
     - **`template_category_mismatch`: a template Meta files as MARKETING (its corrected category if Meta recategorized it, else the declaration) is never sent as `transactional`.** Transactional skips the consent check; Meta's category says what the message is. `template_category_unsupported` for AUTHENTICATION.
     - `content_no_opt_out`: marketing from a version that declares no way to stop (the same rule SMS has for its text).
  5. **Account pacing.** Meta limits how many distinct customers a business can contact outside a conversation in a moving 24 hours (250 to start, then 2,000, 10,000, 100,000, unlimited; per business portfolio; no error code is documented for reaching it). The gate counts, per WhatsApp account, the distinct customers it allowed in the last 24 hours; at the account's `daily_recipient_limit` (config; the starting tier of 250 until the tenant sets its real tier) a message to a new customer is **deferred** (`account_pacing`) until the oldest one leaves the window, and a customer already in the window is not counted again. A message that would expire before then is refused at once with `account_limit_reached`, so a campaign's results say why instead of showing a silent expiry a day later. WhatsApp template messages live **3 days** by default (the 24-hour default would have let every paced message expire as it became sendable; found by the integration test). Throughput is not paced: dispatch is sequential, far below Meta's default of 80 messages per second, and 130429 is retried.
  6. **Error 131049** (Meta held a marketing message back for that customer) is final for the message and is not an opt-out: no suppression, no consent change.
- **Consequences:** + a paused, rejected, recategorized or mismatched template stops at the gate with a named reason, before Meta is asked; + a marketing template cannot be sent without consent by calling it transactional; + a campaign larger than the account's limit continues the next day instead of failing; + the email UI keeps working: WhatsApp templates are labelled in the list, shown read-only with their Meta status, problems and value sources, and kept out of the email pickers of journeys and campaigns. − Pacing counts per account, Meta counts per business portfolio: a tenant with several numbers in one portfolio must set the limit accordingly; − the mirror is only as fresh as the last webhook or check (an hour at worst); − registration is through the API until WP-40b's editor; − the cleaning rules for values and the header and URL-button send shapes come from the documentation and the mock, not yet from Meta (WP-40c live check).
- **Not verified live:** the template listing's permission (expected `whatsapp_business_management`; the endpoint page does not state it), the status webhook's real deliveries, header and URL-button sends, which characters Meta refuses in a value, and how the real messaging limit shows itself when reached.

## Addendum (WP-40b, 2026-11-23): WhatsApp in journeys, campaigns, segments and customer entry

- **Journeys.** A message step's `channel` is `email` or `whatsapp`, and its template must be a template of that channel (checked on save, approval and activation: `"<key>" is a WhatsApp template; this step sends email`). The engine builds a WhatsApp step's message from the registration (`createWhatsappTemplatedMessageOn`, same transaction and idempotency key as email) through the tenant's one active WhatsApp account (`no_whatsapp_account` / `whatsapp_account_ambiguous` otherwise). **Activation** refuses a WhatsApp step whose template Meta would not take now (known problems always; never seen at Meta in live mode only, as the gate), and a marketing template on a transactional step. Saving a draft does not check Meta, so a journey can be built while Meta reviews.
- **WhatsApp, else email.** Branch conditions may read `consent.<channel>` (granted or revoked) and `reachable.<channel>` (true when a marketing message on that channel could reach the customer: consent granted, an active address or number, not suppressed), only in branches, read in one query when a branch asks. The editor has a "WhatsApp, else email" preset (branch on `reachable.whatsapp`, a WhatsApp step, an email step, an end). The gate still judges every message; `reachable` only chooses the route.
- **Segments.** `consent.whatsapp` next to `consent.email`, and `contact.email` / `contact.phone` (exists or not). Consent is now read by a subquery per field instead of one join, so any channel can be asked.
- **Campaigns.** The channel is the template's: a WhatsApp template sends WhatsApp. The audience is the segment AND WhatsApp consent AND a phone number; readiness is per channel (account, rate card, budget, readiness items in live mode; the public unsubscribe links only for email) plus `template_not_sendable` when Meta would not take the template. Results list messages waiting (`waitingBecause`: quiet hours, the account's daily limit) apart from blocked ones. No migration: the campaign's channel is read from its template.
- **Customer entry.** "Add customer" records WhatsApp consent with the same evidence rule as email (a note of where they agreed), and needs the phone number.
- **Templates screen.** WhatsApp templates are created and versioned in the app: pick one Meta lists (fills the name, language, category and approved body) and say where each `{{n}}` comes from; a preview shows the filled text with the value names.
- **Copy drafts** (AI) stay with email steps: WhatsApp text is what Meta approved.

## Addendum (WP-40c, 2026-11-23): operating WhatsApp

- **Settings > WhatsApp** (`GET /api/engage/whatsapp/setup`, tenant admins) is read from state the server already keeps and never calls Meta: the account (ids, mode; never a secret or a number), the webhook URL built from `ENGAGE_PUBLIC_API_URL` (https only; otherwise the reason), the three fields to subscribe, the last delivery report and the last template update Meta sent, the template check, the account's daily limit against the customers messaged in 24 hours and the messages waiting for it, the templates in use with Meta's status, the WhatsApp readiness, and a checklist decided on the server. **Check now** is the existing template check; it doubles as the token check (no second call to Meta).
- **"In use"** means an active journey version has a WhatsApp step with that template (its pinned registration version, else the newest), or the gate allowed a WhatsApp message made from it in the last 7 days. A template nobody uses is shown on the Templates tab, never alerted on.
- **Alerts.** Two are tenant attention items, shown on Settings at once and turned into ops alerts by the ops check: `whatsapp_template_unhealthy` (a template in use is PAUSED, DISABLED, REJECTED, DELETED, PENDING_DELETION, ARCHIVED or LIMIT_EXCEEDED: critical, its messages are refused; quality RED alone: warning) and `whatsapp_template_check_failing` (3 failures in a row, with the code). Two are ops rules per WhatsApp account: `whatsapp_frequency_limited` (131049 failures at least 5 and 10% of at least 20 sent in 24 hours; warning, informational: not an opt-out) and `whatsapp_pacing_holding` (a message whose latest gate decision is `account_pacing` was first held over 24 hours ago). The thresholds are ours, not Meta's, and can be changed with `ENGAGE_OPS_WA_FREQUENCY_*`.
- **Adding the account** from a terminal: `engage:add-account --whatsapp` sets channel, provider and the three secrets, and warns when `phone_number_id` or `waba_id` is missing. Config values whose key ends in `_id` stay text: Meta's ids can exceed JavaScript's safe integers (found while building; the parser used to turn every number-looking value into a number).
- **No migration.** Not verified live yet (the live check): the listing permission, real template status webhooks, header and URL-button sends, the characters Meta refuses in a value, how the real messaging limit shows itself.
