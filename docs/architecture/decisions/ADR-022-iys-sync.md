# ADR-022: İYS sync pulls recipients' changes and pushes the tenant's opt-outs, by the tenant's own credentials

- **Status:** Accepted (2026-11-22, WP-26)
- **Context:** For Turkish commercial messages İYS is the register of consent. Two things must hold: an opt-out the tenant receives is reported to İYS within three business days (regulation Art. 9(6)), and a recipient who revokes in İYS itself (their app, the 3338 number, the İYS page) must stop receiving our marketing, although the tenant is told nothing. ADR-004 already made opt-outs instant locally and the schema anticipated İYS (`consents.source = 'iys'`, `consents.iys_synced_at`). Messign is not an İYS integrator (`docs/compliance/tr-messaging-obligations.md`): the tenant brings its own İYS API access. The only readable specification is İYS's official one (https://apidocs.iys.org.tr, version 3.2.4, read 2026-11-22; the page is built in the browser, so it needs a real browser to read). No tenant has credentials yet, so everything is built against a mock built from that specification.
- **Decision:**
  1. **The tenant's credentials are a channel account of channel `iys`** (migration 134): config `iys_code` and `brand_code`, secrets `username` and `password`, provider `iys` (mode `test` is İYS's sandbox `https://api.sandbox.iys.org.tr`, `live` is `https://api.iys.org.tr`) or `mock`. So they get the per-tenant encryption, rotation and key re-wrapping of every credential. One active İYS account per tenant. It can carry no message (`messages.channel` stays email/sms/whatsapp, `messagingChannel()` refuses it). The address the client calls is fixed by provider and mode, never typed by a tenant; `mock` uses `ENGAGE_IYS_MOCK_URL`, which must be a loopback address the operator set.
  2. **The client** (`engage/iys/client.ts`) uses only what is needed, as documented: `POST /oauth2/token` (password, then the refresh token; access 2 h, refresh 4 h; a token is reused, not fetched per call), `GET /sps/{iysCode}/brands`, `POST /v2/sps/{iysCode}/brands/{brandCode}/consents` (the idempotent version: the same request returns the same `transactionId`, so a retry after a crash registers nothing twice), `GET /sps/{iysCode}/brands/{brandCode}/consents/changes` (`source`, `limit` up to 1000, `after`). Errors are `{errors:[{code, message}]}`; the client keeps İYS's code, the HTTP status and the `X-Trace-Id` header (İYS asks for it in support requests) and logs nothing else. Limits honoured: requests are spaced for 10 a second per IP; a per-second 429 (H083, H124) is waited out; an hourly one (H084 tokens, H086 status, H089 history) is raised to the caller, which must not call again early because that restarts İYS's counter. Not used: the single and multiple status queries, asynchronous batches, the reconciliation file, ViA, retailers, the push connection.
  3. **Push (opt-out to İYS).** A trigger on the consent ledger (`engage.enqueue_iys_opt_out`) queues every opt-out in the transaction that records it, so no route (unsubscribe link, STOP, API, web, import) can forget to report. It queues only an opt-out that has something to revoke: a grant exists earlier for that profile and channel (İYS refuses a first record that is a RET, H175), the tenant has an active İYS account, the channel is email, SMS or call, the profile has an address, and the opt-out did not itself come from İYS. The queue row (`engage.iys_outbox`) is the audit: status, outcome, attempts, İYS's transaction id, and the address only until the row is final. Reported as `RET`, source `HS_EPOSTA` (unsubscribe link), `HS_MESAJ` (STOP keyword), `HS_WEB` (web), `HS_EORTAM` (API and import); `HS_KARAR` is not used (it is for the provider's own decision, and İYS refuses it for a first registration). **This mapping is a reading of the documented definitions, to be confirmed in İYS's sandbox with the tenant.** The consent date is the moment of the opt-out, in Turkish time.
  4. **What each İYS answer means** (documentation error table): 200 sent (registered); H174 (status must change, İYS already holds RET) sent (already current); H175 skipped (not in İYS); H178 (older than İYS's date, someone acted in İYS since) skipped (superseded); H467 (older than three business days) failed (deadline missed); H453 (two operations a day for one recipient) retried after six hours; a rate limit or 5xx or no answer retried with a backoff of 1, 2, 4 … 60 minutes (an hourly limit stops the run); 401 or 403 stops the run for 15 minutes; any other 4xx failed (rejected); after 100 attempts failed (gave up). Before calling, a report past its deadline is not sent: failed (deadline missed) if it sat waiting, skipped (historical) if it was already past the deadline when queued (an imported opt-out from last year), which is not a breach.
  5. **Pull (İYS to the ledger).** The listing returns the last 7 days, older than one hour, oldest first; `after` is the marker of the last movement (`<epoch seconds>_<transactionId>`). Only `source=IYS` is pulled (what recipients did); what the provider reported (`HS`) is ours. Each movement is matched to a profile by its active email or phone (never an erased one), recorded once in `engage.iys_changes` by İYS's transaction id (no address kept), and applied to the consent ledger as source `iys` (ONAY granted, RET revoked) with `recorded_at` the date the recipient acted and `iys_synced_at` set. The consent state keeps the newest decision, so a later local grant is not undone by an earlier İYS revocation and an earlier one is. The marker moves in the same transaction as its page: a crash repeats at most the last page and nothing is applied twice. A pull that fails (İYS down, a limit, credentials) changes nothing and is recorded with İYS's code; `last_pull_at` moves only on success. A revocation from İYS does not add an address suppression (it is a consent decision, not a hard opt-out), so transactional mail continues and a later ONAY from İYS can grant again.
  6. **The send gate is unchanged.** It reads the consent state, so a pulled revocation blocks the next marketing send (`no_consent`) with no new rule. Acceptance test: a recipient revokes in the mock İYS, the pull applies it, and the real gate blocks the message that was queued, while a bystander's message is sent.
  7. **SLA monitor** (`engage/iys/report.ts`, `GET /api/engage/settings/iys`, admin). Reports: target is the same day; an opt-out still waiting after 24 hours is `late`, after two business days `at_risk`, past three `breached`. A pull is `ok` within 2 hours of its last success, `stale` up to 72 hours, `critical` beyond (İYS lists only 7 days, so a pull that stops for good loses recipients' opt-outs) and `never` before the first. Health is `critical` for a breach, a missed deadline or a critical pull; `warning` for anything late, at risk, rejected, stale or never. Business days are Monday to Friday in Turkish time; public holidays are not known, which only makes a deadline earlier. `POST /api/engage/settings/iys/check` gets a token, lists the brands and looks for the configured brand number; it changes nothing in İYS.
  8. **The job** `engage/iys-sync` (pg-boss, every ten minutes) lists tenants with an active İYS account through an id-only SECURITY DEFINER function (`engage.iys_sync_work`, in the isolation allow-list) and, for each, pushes then pulls. İYS's limits are per IP, and every tenant calls from this server's address: 100 history listings an hour shared by all tenants, so a pull every ten minutes (6 an hour per tenant) fits a few tens of tenants; beyond that the pull needs one address per tenant or a different cadence.
  9. **Mock İYS** (`engage/iys/mock/mockIysServer.ts`, `npm run engage:iys-mock`): the token and refresh flow, brands, add consent (v1 and v2), and the movement listing with its marker, 7-day window, one-hour delay and 204, with the documented validation and error codes (H110 to H121, H157/H158, H162, H174, H175, H178, H453, H467 and the rate-limit and auth codes). Tests drive it with recipient actions and injected faults.
- **Consequences:** + an opt-out cannot be recorded without being queued for İYS, and the queue says exactly where each one stands; + a recipient's revocation in İYS reaches the send gate within ten minutes plus İYS's own one-hour delay, with no gate change; + nothing is applied or reported twice (transaction ids, v2 idempotency, marker in the page's transaction); + no address in logs, in `iys_changes`, or in a finished queue row. − the mock follows the documentation, not a real İYS, so real behaviour can differ: **the first live check with a tenant's credentials is the first onboarding step** (`docs/runbooks/iys-sync.md`); − a revocation in İYS is visible to us only after İYS's one-hour delay and our next pull, so up to about 70 minutes can pass (a send in that window cannot see it; the regulation's limit is three business days); − the source mapping of point 3 is unconfirmed; − İYS's per-IP limits are shared by all tenants.
- **Not in v1:** pushing grants (ONAY) to İYS, the daily reconciliation file and the initial import of what İYS already holds (a tenant's CSV with evidence, WP-09, is the starting point), İYS's push connection for movements, per-recipient status checks before a send, sub-brands and retailers, iş ortağı (integrator) access, a gate rule that denies marketing while the pull is stale, an email to the tenant (the Settings screen shows the report in an İYS card, the "needs attention" list and the tab dot, added 2026-11-22; see ADR-020 point 9), and a readiness item for the tenant's IP registration with İYS.
