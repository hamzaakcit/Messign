# ADR-010: One migration runner, a baseline taken from the live schema, no new runtime DDL

- **Status:** Accepted (2026-11-08, WP-03)
- **Context:** The schema was spread over three places: 110 files in `server/src/migrations/` (duplicate numbers, un-numbered files), 24 overlapping files in `server/src/db/migrations/` plus `schema.sql`, and DDL run at boot. Nobody could build a database that matched production: the old runner fails on an empty database (WP-03 found this). Several one-off scripts applied SQL outside any record.
- **Decision:**
  1. `server/src/migrations/000_baseline.sql` is the production schema as of 2026-11-08, from `pg_dump --schema-only --no-owner --no-privileges -N pgboss -T public.schema_migrations` (PostgreSQL 17.8). Only mechanical edits (psql meta-commands, a PG17-only setting, a `search_path` reset); the header in the file says exactly which. It excludes schema `pgboss` (pg-boss manages it), `schema_migrations` (the runner owns it), ownership and grants (roles are set up under `db/scripts/`) and all data. It needs the `pg_trgm` and `vector` extensions.
  2. `server/src/migrations/runner.ts` (`npm run db:migrate`) is the only way to change schema. It applies files in name order inside one transaction each, records them in `public.schema_migrations`, and takes an advisory lock so two instances cannot race.
  3. **Baseline adoption:** on an empty database the baseline runs. On an existing database it is recorded as applied without running, but only if every table it defines exists; otherwise the runner refuses and writes nothing. Production therefore adopts it, then applies only later migrations.
  4. New migrations are `NNN_snake_case.sql` with NNN above the last one. The baseline is never edited. A test enforces naming and uniqueness.
  5. **No new runtime DDL.** A test fails if any TypeScript file outside an allow-list contains DDL, and the allow-listed (frozen, pre-existing) files may not gain more. Remove entries as that code is retired.
  6. The 110 legacy migrations, `server/src/db/migrations/`, `schema.sql` and the scripts that only applied them were deleted. They remain in git history before the WP-03 commit.
- **Verification:** a database built from the baseline matches production on a text diff of `pg_dump -s` except 96 CHECK expressions that PostgreSQL 17.8 and 17.11 print differently (same constraint); CI instead compares 15 structural counts against the live values. The integration suite builds the schema with the real runner, which also tests migration 111 and engage provisioning against the real tables (it caught a missing `reimbursement_users.tenant_id`).
- **Consequences:** + a fresh database equals production; schema history is one file plus numbered migrations; CI proves it. − the baseline needs pgvector (CI uses `pgvector/pgvector:pg17`); − Postgres 16 without pgvector cannot run the database tests (they skip); − the old per-migration history is only in git; − RLS scripts under `db/` still sit outside the runner (already reflected in the baseline's policies).
- **Rejected:** replaying the 110 old files (does not reproduce production); keeping both folders; a checksum table (the baseline is read-only by convention and test).
