# ADR-011: Journey definitions are immutable versions; activation needs a recorded approval, enforced by the database

- **Status:** Accepted (2026-11-09, WP-15)
- **Context:** A journey sends marketing messages on its own once it runs. Principle 7 requires explicit human approval, permission checks and an audit trail before anything sends; principle 4 asks for enforcement at the schema level for legal surfaces. The roadmap suggested reusing "the existing approval queue", but that queue (`marketing_approval_queue`) is a Company-OS table without RLS, pinned to the `messign` organization (current-state §3), so engage data cannot go there without breaking tenant isolation (ADR-002).
- **Decision:**
  1. `engage.journeys` (tenant, key, name) and `engage.journey_versions` (immutable definition, schema version 1). A change is a new version. Migration `120_engage_journeys.sql`.
  2. Lifecycle per version: draft → approved → active → retired, each step once, never back, each with who and when. The database enforces it: a CHECK forbids activation without approval (the WP-15 acceptance criterion, which holds even for the database owner), a trigger forbids changing the definition or undoing a step, a partial unique index allows one active version per journey, and the engage role has no DELETE and may update only the lifecycle columns.
  3. Activating a version retires the active one in the same transaction (advisory lock per journey). A retired version is never reactivated; rolling back means publishing the old definition as a new version, which needs its own approval.
  4. Approval lives in engage (on the version row), not in the Company-OS approval queue. Only tenant admins create, publish, approve, activate and stop; members read and validate.
  5. The definition schema (zod, `engage/journeys/definition.ts`) is strict: unknown keys are errors, the step graph must be acyclic with every target existing and every step reachable, conditions nest at most four levels and `event.*` fields are allowed only where an event is evaluated. Message steps name a template by key (optionally a version) that must exist in the tenant when a version is created, approved and activated.
  6. **Not in v1:** webhook steps (no customer needs them yet, and calling arbitrary URLs from the engine needs SSRF protection), SMS/WhatsApp message steps, holdout and re-entry enforcement (WP-17; `re_entry` is stored). The executor came with WP-16 (ADR-012).
- **Open (D-13):** whether the approver must be a different person from the author. Today the author may approve their own version: most pilot tenants have one admin, and a two-person rule would block them. Every approval is recorded either way.
- **Consequences:** + an activated journey always traces to an approved, unchanged definition and a named approver; + misconfigurations (loops, dangling steps, missing templates) are caught before anything runs. − no in-place edits or reactivation; every change is a new version and a new approval.
