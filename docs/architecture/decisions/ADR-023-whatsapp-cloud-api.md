# ADR-023: WhatsApp goes out through the Cloud API with approved templates, and every way a customer says stop is honoured

- **Status:** Accepted (2026-11-22, WP-27)
- **Context:** WhatsApp is the second channel (target-state E). The platform already had the pieces around it: the consent ledger and send gate know the channel (marketing needs consent for it and, from ADR-004, a template), the readiness list names `waba_verified`, and the mock adapter can carry it. What was missing is a real adapter, the way Meta's webhooks reach us, and the opt-outs WhatsApp itself raises. Built from Meta's official documentation (developers.facebook.com, WhatsApp Business Platform, read 2026-11-22: Messages API, template messages, webhook endpoint, messages and user_preferences webhook references, error codes). There is no tenant Meta app yet; everything is tested against a mock built from those pages, and a Meta test number comes with the tenant (docs/runbooks/whatsapp.md).
- **Decision:**
  1. **The tenant's own business number.** A channel account of channel `whatsapp`, provider `whatsapp_cloud`: config `phone_number_id` (and optionally `api_version`, default `v23.0`, and `default_language`, default `tr`); secrets `access_token` (a system user's token), `app_secret` (signs the webhooks) and `verify_token` (the handshake word, chosen by us). Mode `test` is a Meta test number, `live` a verified number. Same per-tenant encryption and rotation as any credential. The address is `graph.facebook.com`; only the operator can point it at a loopback mock (`ENGAGE_WHATSAPP_GRAPH_URL`), a tenant cannot.
  2. **Sending** (`engage/whatsapp/whatsappAdapter.ts`): `POST /<version>/<phone number id>/messages`. Content is `{template, language?, body_parameters?}` (an approved template and its positional variables) or `{text}`. A text message works only inside the 24-hour customer service window (Meta error 131047 otherwise), so **marketing uses templates only**, which the send gate already required (`content_no_template`); the gate now also refuses a template name WhatsApp could not have (`content_template_invalid`: lower-case letters, digits, underscores). Nothing about a message is sent before the gate allows it, and the adapter never decides that.
  3. **Not idempotent.** The Cloud API has no idempotency key. A send that Meta accepted but whose answer was lost is sent again by the retry: a rare duplicate, never a lost message. An answer that is accepted but carries no message id is final (it cannot be told from lost, and a retry could duplicate it).
  4. **Errors** are read from Meta's numeric `error.code` only (never the text), as `wa_<code>`. Retried: 2, 4, 80007, 130429, 131000, 131016, 131056, 131057, 133004 (downtime and rate limits). Final: everything else in the table (credentials 0/3/10/190/131005, account restrictions 368/130497/131031, template problems 132000 to 132016, a closed window 131047, an undeliverable number 131026, a healthy-ecosystem refusal 131049, a spam restriction 131048, a bad request 100/131008/131009). A code outside the table is decided by its HTTP status (5xx, 429 and 408 retried). **131050, the recipient has stopped marketing messages from the business, is final and is an opt-out** (point 6).
  5. **Webhooks** on the existing signed route `POST /api/engage/webhooks/:accountId`, plus `GET` for Meta's handshake. The handshake (`hub.mode=subscribe`, `hub.verify_token`, `hub.challenge`) answers 200 with the challenge as plain text only for the account's verify token (compared in constant time, a challenge that is not a short token is refused rather than reflected); anything else is 403, an unknown account 404. A delivery is verified by `X-Hub-Signature-256`, HMAC-SHA256 of the exact bytes with the app secret, before anything is read. Statuses become delivery reports: `sent`, `delivered`, `failed` as they are; **`read` becomes `delivered`** (Meta omits "delivered" when a message is read at once); `played` and the unknown are ignored. A status has no event id, so one is made from the message id and the status, and Meta's retries (up to 7 days, batches of up to 1000) repeat it and change nothing. A delivery for another business phone number is ignored. A failed status keeps its first error code. A report about a message not recorded yet is answered 503 so Meta retries, like every provider (ADR-012 note on SES).
  6. **Every way a customer says stop is honoured**, as a revocation of WhatsApp consent with source `stop_keyword` and the number suppressed for WhatsApp, in the transaction that receives it (the same rule as an SMS STOP, ADR-004): (a) a message whose whole text is a stop word (STOP, iptal, dur, durdur, vazgeç, çıkış, unsubscribe, abonelikten çık ...; whole message only, folded for case, accents and punctuation, so "dur bakalım" is not an opt-out), typed or the label of a quick-reply button; (b) Meta's `user_preferences` webhook with value `stop` (the customer stopped marketing messages in the app); (c) error 131050, whether Meta refuses the send or reports it afterwards in a failed status. A `resume` in the app is **not** a grant: consent needs the tenant's own proof, so it only records that it was ignored. Email and SMS consent are not touched.
  7. **What is kept** (migration 135, `engage.inbound_events`): one row per delivery, by Meta's id (the dedupe for retries and the evidence that an opt-out request was received), with its kind, what it did (`opt_out_applied`, `no_opt_out`, `unmatched`, `resume_ignored`) and the profile. No message text, no phone number, no name. Append-only. A message that names no phone number (see consequences) or a number nobody here has is `unmatched` and answered 200, never retried.
  8. **The server's JSON parser must not eat webhooks.** The server parsed every `application/json` body before the engage routes, so the exact bytes a signature needs were gone: Meta posts `application/json`, SES (through SNS) `text/plain`, which is why SES worked. `engage/jsonBodyParser.ts` now leaves `/api/engage/webhooks/` unparsed and is the one parser the server and the test app both use, so the tests run with what production runs. Found while building this; without it every WhatsApp webhook would have been refused with 400.
  9. **Mock Graph API** (`engage/whatsapp/mock/mockGraphServer.ts`): the Messages endpoint with the documented success and error bodies and the codes it can raise (190, 100, 131008, 132001, 132000, 131047, 131050, 131026), controls to approve templates, open a customer service window, stop marketing for a number and inject faults, and builders for Meta's documented webhook payloads (status, incoming message, user_preferences).
- **Consequences:** + a marketing template cannot reach a customer without WhatsApp consent (the acceptance test runs the real gate: a customer with email and SMS consent but no WhatsApp consent is blocked, with it the template goes out); + a customer's stop reaches the ledger in the same request whichever way it arrives, once, whatever Meta retries; + no number, text, token or secret in logs, `inbound_events` or errors. − **customers who use a WhatsApp username may be identified only by Meta's business-scoped user id**: Meta says to build for that, and our profiles know phone numbers only, so such a customer's STOP is recorded as `unmatched` and cannot be applied; matching by id needs a stored id per profile; − a duplicate send is possible after a lost answer (point 3); − the mock follows the documentation, not Meta: the first live check with a Meta test number is the first onboarding step; − a template must be approved in WhatsApp Manager by Meta before it can be sent, and Messign does not manage templates.
- **Not in v1:** journeys that send WhatsApp (the journey schema's message step is email only), templates managed from Messign (creating, listing and reading approval status), named template variables, media, interactive and button messages, business-scoped user ids, the template quality and messaging-limit signals, per-message price tracking from status webhooks, replies to customers, and a screen in Settings for the account.

## Live check (2026-11-22, Meta test number)
Run through the real pipeline in sandbox, with Meta's sample template to the runner's own phone:
- **Passed:** sending (accepted by Meta, delivered to the phone); Meta's webhook handshake on the server; the webhook signature; delivery reports (`sent`, then `delivered`, applied once through the signed webhook); a customer's **STOP** reply (consent revoked with source `stop_keyword` and evidence `whatsapp_stop_message`, the number suppressed for WhatsApp, an `inbound_events` row `text -> opt_out_applied`, no text or number stored); and the gate then blocking a marketing send to that customer (`blocked (suppressed)`, nothing reached Meta).
- **Found and fixed:** delivery reports did **not** arrive until the app was subscribed to the WhatsApp Business Account itself (`POST /<WABA id>/subscribed_apps`); the callback URL and fields on the app are not enough, because Meta's own test app was the only one subscribed to the account. `engage:whatsapp-check --webhooks --subscribe` does it; the runbook has the step.
- **Not verified live:** Meta's `user_preferences` stop (the app's own option) and error 131050 (they apply to marketing-category templates, and the test number only has a sample template); a business-scoped user id in place of a phone number; the sender name and logo (the test number's profile cannot be edited, so that needs a real number); a permanent system-user token.
