# ADR-007: Journeys trigger from persisted events, never from the in-process mitt bus

- **Status:** Accepted (2026-11-07, with D-01)
- **Context:** A10 refuted: the mitt bus is in-process, synchronous, swallows errors, and loses events on restart or with multiple replicas.
- **Decision:** Ingested events are committed to `engage.events` together with a pg-boss trigger-evaluation job in one transaction. Journey triggers, waiters and exit checks read from the database. The mitt bus may still be used for UI/socket notifications about engage activity (best effort), never for correctness.
- **Consequences:** + no lost triggers; replayable. − slightly higher latency (job pickup interval, ~1–2s), acceptable for marketing journeys.
- **Rejected:** Redis pub/sub swap of the bus (still not durable); Kafka (operational weight).

## Implementation notes (WP-08, 2026-11-08)
- **Migration `114_engage_events.sql`:** `events` (partitioned monthly on `occurred_at`), `event_keys`, `trigger_outbox`; forced RLS on all three. Events and their keys are immutable for the engage role.
- **Dedup** lives in `event_keys (organization_id, client_event_id)`, not in an index on `events`: a unique index on a partitioned table must include the partition key, so it could not catch a replay carrying a different timestamp. Claiming the key, inserting the event and inserting the outbox row happen in one transaction, one savepoint per event. A rejected event never claims its id, so a corrected resend is accepted. Keys are kept after partitions are dropped, so a replay of an old event stays a duplicate.
- **Transactional enqueue:** the outbox variant ADR-007 allows. The pg-boss job and drain come with the executor (WP-16); until then rows stay `pending`. The engage role can only mark an outbox row processed.
- **Partitions:** `engage.ensure_event_partition(ts)` creates the month's partition on first use. It is a SECURITY DEFINER function that can only create partitions of `engage.events`, refuses timestamps outside [now - 400 days, now + 2 days], serialises on an advisory lock, and revokes the engage role's direct access to the partition (rows are reached through the parent only). This is the one sanctioned runtime DDL; it replaces the creator job. A test caught a real race in the first version (the post-lock existence check used `to_regclass`, which does not see a partition another transaction just committed); it now uses a catalog query. Retention (drop by partition, default 13 months) is not scheduled yet.
- **API v1** under `/api/engage/v1`, authenticated by API key (`ingest` scope; `journeys:trigger` for the trigger route), then a per-key rate limit (default 600 requests per minute, `ENGAGE_INGEST_RATE_LIMIT`; per process, so approximate with several replicas):
  - `POST /profiles:upsert`: identifiers normalized; changing an email or phone keeps the old value as history, which is the "identify/update" operation; consents optional, atomic with the profile; the tenant may claim only sources `api`, `web`, `import`; a grant needs evidence; 409 if the email or phone belongs to another profile. `skip_triggers` is accepted and has no effect until WP-16.
  - `POST /events:track`: up to 500 per request, one result per event (`accepted`, `duplicate`, `rejected`). Rejected individually: unknown or erased profile, timestamp more than 5 minutes ahead or older than 399 days, missing required properties for the five reserved events. Names are `lower_snake_case`; properties up to 8000 bytes. An unexpected database error fails the whole request with 500 and is safe to retry.
  - `POST /journeys/:key/trigger`: validates and checks the profile, then answers 501 until WP-16.
  - `GET /openapi.json`: the published contract (`engage/openapi.ts`); a test fails if it drifts from the routes.
- **Strict bodies:** any unknown field, including a body `organization_id`, is a 400. Validation errors name fields and never echo values.
- **Not done:** pg-boss drain and trigger evaluation (WP-16), retention job, shared rate-limit counter (WP-31), SDKs.
