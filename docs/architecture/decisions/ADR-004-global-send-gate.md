# ADR-004: One send gate, default OFF, with per-tenant legal readiness and a decision ledger

- **Status:** Accepted (2026-11-07, with D-01)
- **Context:** Existing adapters go live on token presence or `*_FORCE_REAL` flags with inconsistent polarity. The publisher cron runs every minute by default. No consent/suppression checks exist.
- **Decision:**
  1. `SEND_MODE` env = `off` (default, also when unset or invalid) | `sandbox` (only mock adapters and test-mode accounts) | `live`.
  2. `engage.tenant_readiness(organization_id, channel, item, value, evidence_url, recorded_by, recorded_at)`: e.g. `iys_brand_code`, `btk_sender_id`, `email_domain_authenticated`, `waba_verified`, `dpa_signed`. `engage.tenant_settings.send_enabled` defaults false and can only be set true when the required readiness items for that channel exist.
  3. A single `sendGate.evaluate(request)` is the only path to an adapter. It writes `engage.send_decisions` (allow/deny + every reason) **before** the provider call. It fails closed on any exception.
  4. Rules in order: global mode → tenant send_enabled → channel account active and mode-compatible → readiness → suppression → consent (marketing) → quiet hours (marketing) → frequency cap (marketing) → budget cap → content checks.
  5. Legacy: `MARKETING_PUBLISHER_ENABLED` default flips to OFF. Legacy adapters must also consult `SEND_MODE` (a one-line guard) until the publisher is removed.
- **Consequences:** + one auditable kill switch; legal readiness is explicit data, not tribal knowledge. − every new adapter must go through the gate (intended).
- **Rejected:** per-adapter flags; gate checks inside journeys only (would miss API-triggered and manual sends).

## Implementation notes

### WP-10 (messaging core, interim gate)
- **Where:** `server/src/engage/messaging/`. `adapter.ts` is the provider-neutral contract (`capabilities`, `send`, `parseWebhook` with signature verification, `normalizeError`) and a registry keyed by the account's `provider`. `dispatch.ts` is the only code that calls `adapter.send()`; a test enforces that, and that only the messaging module resolves adapters.
- **Interim gate, until WP-11 replaces it.** `dispatchMessage` applies a deliberately small and strict rule set: `SEND_MODE` off (unset, empty or invalid) leaves the message queued and untouched; `sandbox` allows only the mock adapter on a `test` account; `live` is refused outright (`live_not_available`), because the full gate does not exist yet; a marketing message needs a current consent grant; any message to a suppressed address is blocked; a profile without an address for the channel is blocked. A denial is recorded as a `blocked` event (final). **There is no `send_decisions` table yet**: the reason is in the `blocked` event's `error_code`. WP-11 must replace `interimGate`, not wrap it, and add the decision row before the provider call.
- **Not yet in the gate:** tenant `send_enabled`, readiness, quiet hours, frequency cap, budget cap, content checks.
- **Ledger.** `engage.messages` (one row per intended message, unique `(organization_id, idempotency_key)`) and append-only `engage.message_events`. `messages.status` is derived from the events by a trigger and cannot be written by the engage role; `attempt_count` and `claimed_at` change only through `engage.claim_message`. Status ranks: queued 0, sending 1, sent 2, delivered/failed/blocked 3, bounced 4; a status only moves up, so duplicate and out-of-order reports never move a message back. Two different final reports (delivered vs failed) are decided by arrival: the first wins. A bounce may follow a delivery, because email bounces arrive late. `retry_scheduled` is the one step back (sending to queued).
- **Idempotency.** The same key and the same request returns the existing row; the same key with a different request is an error (`IdempotencyConflictError`); the provider call carries the key. A worker that dies after claiming is recovered after the lease (default 5 minutes): the retry reuses the key. For a provider that cannot deduplicate, a crash between "provider accepted" and "recorded" can still send twice; the mock deduplicates, real adapters must state what they do.
- **Not stored:** the recipient address (resolved from the active identifier at send time) and anything personal in events. `content` holds the rendered message and is personal data; WP-35 must pseudonymise it on erasure.
- **No public webhook route yet.** `ingestWebhook(orgId, accountId, raw)` verifies and applies a delivery; the unauthenticated HTTP route, which has to find the tenant from the account, arrives with the first real adapter (WP-12).

### WP-11 (full gate; replaces the WP-10 interim gate)
- **Where:** `server/src/engage/messaging/gate.ts` (`evaluateGate`), configuration in `gateConfig.ts`, migration `117_engage_send_gate.sql`. The interim gate is gone.
- **R-1 is enforced by the database, not by convention.** `engage.claim_message` now takes a decision id and refuses unless it is an ALLOW decision for that same message, in the same tenant, written in the last two minutes. Only `gate.ts` inserts into `send_decisions` (test-enforced), and the table is append-only.
- **Outcomes.** `hold` (no row): `SEND_MODE` off, or tenant `send_enabled` false (or no settings row). Both are read again for every message, so either switch stops a running batch at the next message. `defer`: the only failure is quiet hours; the message stays queued with `next_attempt_at` at the end of the window. `deny`: any other failure, final (`blocked` event). `allow`: the cost is reserved on the message and the claim may proceed.
- **Rules, all evaluated, all recorded** (first failure is the decision code): expiry (`messages.expires_at`, default 24 h, so a message held by a kill switch is not sent days later) → account active and mode-compatible (sandbox needs a `test` account, live a `live` one) → readiness (live only; `REQUIRED_READINESS` per channel: email `dpa_signed`, `email_domain_authenticated`; sms `dpa_signed`, `btk_sender_id`, `iys_brand_code`; whatsapp `dpa_signed`, `waba_verified`) → recipient → sandbox allow-list (`engage.send_allowlist`, normalised like identifiers) → suppression (address-level, every purpose, whichever profile holds the address) → consent (marketing) → quiet hours (marketing, tenant time zone, computed by Postgres) → frequency cap (marketing; default 3 per 168 h per profile and channel; tenant-configurable) → rate card and monthly budget (all purposes) → content checks.
- **Budget (ADR-008).** The latest rate card in effect for (channel, purpose, route) gives the estimate. Month-to-date spend is the sum of reserved estimates of other messages this calendar month in the tenant's time zone, excluding blocked messages and failed messages the provider never accepted. A retry keeps its first reservation. Decisions are serialised per tenant and channel with an advisory lock, so concurrent sends cannot overshoot the cap. A reservation, once made, cannot be changed (trigger; this stops a superuser too). Missing rate card, missing cap or mismatched currencies deny.
- **Content checks** catch obvious omissions only; they do not certify that a message is lawful. Marketing email needs an `https` `unsubscribe_url` that appears in the body; SMS needs a sender ID of 3 to 11 ASCII letters, digits, space, dot or dash (from the content or the account config); marketing SMS needs the word `iptal` or `stop` (Turkish case folding); marketing WhatsApp needs a template.
- **Fail closed.** An exception during evaluation records a `gate_error` denial; if even that cannot be written, the message is held.
- **Deliberately not done here:** setting `send_enabled` (WP-22 sets it only when readiness exists; until then operators use SQL), settings and allow-list HTTP routes (WP-22), multi-segment SMS cost (one unit per message), provider actual cost (`cost_actual_minor`).

### WP-12 (email adapter, provider webhooks)
- **Adapter:** `server/src/engage/messaging/sesAdapter.ts`, Amazon SES API v2 per D-05 (Messign-owned sandbox account now; the tenant's own SES account at business start through the same adapter). Request signing (`sigv4.ts`) is written out rather than taken from the AWS SDK and reproduces AWS's published SigV4 test vector. Each mapping cites the AWS page it follows. Setup steps: `docs/runbooks/ses-sandbox-setup.md`.
- **Webhooks:** `POST /api/engage/webhooks/:accountId` (`webhookRoutes.ts`, migration 118). No user or key: the account's adapter verifies the provider's signature over the exact bytes. For SES that is the SNS signature (versions 1 and 2), with the signing certificate fetched only from `https://sns.<topic region>.amazonaws.com/*.pem`, and **only the account's own `sns_topic_arn` is accepted**, because any AWS customer can send validly signed SNS messages to the URL. Subscription confirmations are verified, then confirmed by visiting `SubscribeURL` (same host rule). The tenant is found by a pre-auth policy that exposes exactly one `channel_accounts` row (like the API-key lookup). The isolation suite accepts that policy and the route's guard explicitly, and nowhere else.
- **Effects:** Delivery → delivered; Permanent bounce → bounced and the address suppressed (`hard_bounce`, or `opt_out` for SES list-management unsubscribes); Transient or Undetermined bounce → failed, no suppression (SES reports a soft bounce only once it has stopped retrying); Complaint → a `complained` event (no status change) and the address suppressed (`complaint`), except `not-spam` feedback. Suppression is written in the same transaction as the event, only when the report matches a message of that tenant, so the gate denies the next send at once (R-3). Opens, clicks and delivery delays are ignored.
- **Report-before-bookkeeping race (found on the first real send):** the SES message id is stored only after the send call returns, and SES can report delivery before that. The first version answered 200 for a report about an unknown message, so SNS stopped retrying and the `delivered` report was lost. The route now answers 503 when any report is unmatched; matched events are already stored and repeats are skipped by the unique provider event id, so a retry is safe. Reports for messages that never existed here exhaust SNS's retries and are dropped, as before. A report lost this way before the fix stays lost (the first real test message remained `sent`).
- **Not done:** `List-Unsubscribe` headers and the one-click endpoint (WP-13); a complaint does not also revoke the consent record (the suppression already blocks every send); SES has no idempotency key, so a crash between "SES accepted" and "recorded" can send twice; nothing has been run against real AWS yet.
