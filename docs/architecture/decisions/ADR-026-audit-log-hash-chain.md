# ADR-026: The engage control plane writes a tamper-evident audit log from database triggers, one hash chain per tenant

- **Status:** Accepted (2026-11-23, WP-31)
- **Context:** Before real data, a tenant (and we) must be able to answer "who turned sending on, who changed the cap, who approved that journey, which key was revoked", and to notice if that history was edited. Until now the answer was application logs (`logSetting`), which are not stored with the data, can be lost, and prove nothing. The roadmap asked for a hash-chained audit stream for the engagement tables only (technical-debt: platform audit log not hash-chained, two audit systems; fix when touched, engagement stream only).
- **Decision:**
  1. **Record in the database, in the same transaction.** `AFTER` triggers on the control-plane tables (`tenant_settings`, `channel_accounts`, `api_keys`, `tenant_readiness`, `budget_caps`, `rate_cards`, `send_allowlist`, `journey_versions`, `campaigns`, `copy_drafts`; migration 138) call `engage.audit_append`. A change cannot happen without its entry, a refused change leaves none, and no code path can forget (principle 4). There is no write function in application code.
  2. **One chain per organization.** Each entry stores the SHA-256 of `engage-audit-v1 | org | seq | prev hash | time | actor | action | subject | details`. `audit_append` serialises writers per organization with an advisory lock, so there is no gap or fork. `engage.verify_audit_chain(org)` recomputes the chain with the same SQL hash function and returns the first bad position.
  3. **Append-only for everyone.** The engage role has `SELECT` only; a trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` for every role. The one writer is a `SECURITY DEFINER` function that refuses any organization but the session's (the isolation suite lists it among the reviewed definer functions).
  4. **No personal data, no secrets.** Entries hold ids, codes and the changed setting: never a secret or ciphertext, an address or number (an allow-list entry is recorded by id and channel), a customer, or message content. Column allow-lists in the triggers mean a column added later is not recorded by accident. This also keeps the log outside the data-subject erasure of WP-35 (nothing in it identifies a customer).
  5. **Who.** The row's own user column when it has one (`created_by`, `approved_by`, ...), else the actor of the request: the authentication middleware runs the request inside `runAsActor` (`user:`, `platform_admin:`, `api_key:`), `withEngageTenant` copies it into the transaction setting `engage.actor`, and operator scripts label themselves `operator:<script>`. Anything else is `system`.
  6. **Sign-in events** of an engage tenant's users (signed in, failed attempt, locked, password changed, a reused refresh token ended the session) are appended by the auth service through the same function, user id only. Best effort: a failure there never blocks a sign-in.
  7. **Read and verify.** Tenant admin: `GET /api/engage/settings/audit` (entries and chain status). Operator: `npm run engage:audit-verify -- --all | --org <uuid> [--expect-head-seq n --expect-head-hash h]`. The ops check raises `audit_chain_broken` (critical) for a tenant whose chain does not verify.
- **Limits, stated plainly:** this is tamper-**evident**, not tamper-proof. Whoever holds the database owner role can switch the triggers off, edit, and re-chain the whole log; they cannot do it to an entry that someone remembered the hash of. A removed **tail** still verifies; only a head recorded outside the database shows it (hence the weekly head note in the pilot runbook). It records control-plane changes, not every business event: sends have `engage.send_decisions` and `message_events`, consents their own ledger.
- **Not in v1:** an external anchor for the head (a timestamping service or a mirrored table in another database), a Settings screen for the history (the API exists), logging reads, and the platform organization's Company-OS actions (their own legacy audit tables).
- **Evidence:** `engageAudit.integration.test.ts` (every recorded action with its actor; no secret, address or key material in any entry; an edited entry, an edited detail, a removed entry and an entry rewritten together with its own hash are found at the right position; the removed tail passes, as documented; 25 concurrent changes leave a gap-free chain; the engage role and the database owner cannot change entries; tenant privacy; the API; the ops rule), `engageApiKeyAdmin.integration.test.ts`, `engageIsolation.integration.test.ts`.
