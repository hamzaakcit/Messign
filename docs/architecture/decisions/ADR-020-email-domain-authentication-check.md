# ADR-020: The email domain readiness item comes from a DNS check, not from a statement

- **Status:** Accepted (2026-11-20, WP-39)
- **Context:** ADR-004 requires `email_domain_authenticated` before a live email send (the tenant's domain has SPF, DKIM and DMARC). Until now a tenant admin typed a value into Settings and the gate trusted it, so the one readiness item that DNS can settle was the one nobody checked. Gmail and Yahoo reject or spam-folder bulk mail that lacks these records, so a wrong "yes" costs the tenant its delivery and Messign its reputation.
- **Decision:**
  1. **The item is set by a check, never by hand.** `POST /api/engage/settings/email-domain/check` (admin) looks up the domain of the tenant's one active email account's From address, read-only, and records the result. `PUT /settings/readiness/email/email_domain_authenticated` is refused (400, field `item`). Every other readiness item stays a statement the tenant makes.
  2. **What counts.** SPF: exactly one TXT record starting `v=spf1` at the domain. DKIM: for each selector the admin names (1 to 5), a CNAME, or a TXT with a non-empty public key, at `<selector>._domainkey.<domain>`. DMARC: exactly one TXT record starting `v=DMARC1` with a valid `p=` (none, quarantine or reject) at `_dmarc.<domain>`. All three must be found. No named selector is a failure: a domain cannot be shown authenticated without a key, and a DNS zone cannot be listed to find selectors.
  3. **A lookup that fails is not a pass and not "missing".** Timeouts and server errors give the code `lookup_failed`; only "no such name" and "no data" mean absent. Two SPF records, two DMARC records and a DMARC record without a policy are failures with their own codes.
  4. **A pass sets the item, a failure removes it.** Both happen in the same transaction that appends the evidence row. The lookups run outside any transaction (a slow resolver never holds a connection), and the result is discarded with `account_changed` if the active account was replaced meanwhile.
  5. **Evidence is append-only.** `engage.email_domain_checks` (migration 131, forced RLS) holds the domain, the selectors and a small result per mechanism (found or not, a code, the DMARC policy). It never holds the DNS record text. The engage role can insert and read, not update or delete. Checks are throttled to one per ten seconds per tenant.
  6. **A pass expires.** In live mode the gate and the campaign readiness accept the item only if it was recorded in the last 30 days (`EMAIL_DOMAIN_CHECK_MAX_AGE_DAYS`); the admin checks again to renew it. The other items do not expire. Sandbox mode is unaffected (it never required the item).
  7. **Logs carry ids, the domain name and codes**, never record text or addresses.
  8. **A scheduled re-check (added 2026-11-21, migration 132).** An hourly job (`engage/email-domain-recheck`, pg-boss) looks again at every tenant whose item is set and whose latest check is more than 23 hours old (more than 1 hour old if that check could not reach DNS). It uses the selectors of the last check and the *current* From domain of the one active account, appends an evidence row with `checked_by` empty (shown as "checked automatically"), and renews the item (a pass) or removes it (a failure), like an admin's check. Differences: a check whose only failure is `lookup_failed` keeps the item and is tried again within the hour, because a resolver that timed out says nothing about the records; an account that is gone, doubled or without a usable domain removes the item, because the item described an account that no longer sends; an account moved to another domain is checked on that domain, so the item cannot carry over to a domain nobody checked. The scheduler has no tenant: the due list is a `SECURITY DEFINER` function returning organization ids only, and each re-check runs in its own tenant transaction. The renewal means the 30-day expiry (6) is now the backstop for a job that stopped, not a monthly chore.
- **Consequences:** + the live email gate no longer rests on a typed "yes" for the part of the setup that DNS can prove; + a tenant sees exactly which record is missing; + a dropped record is noticed at the next live send after the pass expires, or sooner on a re-check. − the check proves the records exist, not that the provider is allowed to send for the domain (the provider's own domain verification is separate) and not that the SPF record covers the provider (includes are not followed); − a From domain whose DMARC lives only on its parent domain fails (no public suffix list here): send from the parent domain, or publish DMARC on the subdomain; − the re-check runs hourly and checks each tenant about daily, so a record removed after a pass is noticed within roughly a day, and live sends in that window still go out; − a removed item is not announced to the tenant except by the Settings card and the readiness list, there is no email or in-app alert yet.
- **Not yet:** an alert to the tenant when the item is removed, SPF include resolution, DMARC alignment analysis, selectors discovered from the provider's API (it would need an extra permission on the tenant's account), and the same check for an SMS sender or a WhatsApp business account.
