# ADR-013: Segments are immutable, pinned by the journeys that use them, evaluated in SQL; a scheduled run enrolls each customer once

- **Status:** Accepted (2026-11-10, WP-36)
- **Context:** The tenants that cannot send events yet (Q-A) go live on imported data: win-back ("ordered before, not for 90 days") and new-release mailings need an audience defined over order history, attributes and consent, and a way to start a journey for that audience on a schedule. Two risks: an audience that changes behind an approved journey (principle 7), and a scheduled run that enrolls someone twice or whose counts cannot be trusted ("Segment counts match SQL").
- **Decision:**
  1. **Segments** (`engage.segments`, immutable `engage.segment_versions`; migration `124_engage_segments.sql`). A segment is one condition tree (`all`/`any`/`not`, at most four levels) over `attributes.<name>`, `orders.<metric>` and `consent.email`. Order metrics come from the customer's `order_completed` events up to the moment of evaluation: `count`, `count_30d/90d/365d`, `total_spent`, `total_spent_365d`, `days_since_last`, `days_since_first` (whole days; empty for a customer who never ordered). Erased customers are never members. A change is a new version; the engage role cannot update or delete versions.
  2. **Evaluated in SQL only** (`segments/compile.ts`, pure). Every value and every attribute name is a bound parameter; the statement text contains only fixed fragments. Each leaf is `COALESCE(..., false)`, so a missing value never matches a comparison and `not` of it matches, the same as the journey condition evaluator. A test runs both on 259 conditions over 32 customers with awkward values (wrong types, nulls, arrays, empty strings, `%`, quotes) and requires identical answers; another compares segment counts with independently written SQL for 19 definitions (order counts and windows, spend, recency, consent, attributes, erased customers).
  3. **A journey pins a segment version.** New journey trigger `segment {segment, segment_version, every_days, at_local_time}`; creating, approving and activating a journey version checks that the segment version exists. Changing who a journey targets therefore means a new journey version, and a new approval (ADR-011). A segment itself sends nothing and needs no approval.
  4. **Schedule.** Every N days (1 to 365) at a local time of the tenant's time zone, counted from the activation day. The first run is the first such moment after activation, never at once. Only the latest due slot runs: missed slots are not made up (a tick that was down for three days does not send three rounds).
  5. **One run per slot, once per customer per run.** `engage.segment_runs` has one row per (journey, slot): the claim. The segment is evaluated as of the slot. Customers are enrolled in chunks of 500, each in a transaction that locks the run row, reads the cursor (`last_profile_id`, keyset by id) from it and writes the chunk's counts, so counts are exact and an interrupted run resumes where it stopped (a claim older than ten minutes is taken over). The enrollment key is `segment:<slot>:<customer>` (unique per journey, migration 121), so retries and concurrent workers cannot enroll anyone twice. The journey's own re-entry rule decides whether a customer who already took part in an earlier run can enter again (`never`, `after_exit`); a customer still in the journey is never enrolled twice.
  6. **Cap.** One run enrolls at most 100,000 customers; if more match, the run ends with `truncated = true`. A mistaken "everyone" segment stays bounded, and the send gate (consent, frequency cap, budget, sandbox allow-list) still applies to every message.
  7. **Work across tenants.** A third kind of id-only SECURITY DEFINER list, `engage.due_segment_work(orgs)`, names the active segment-triggered journeys. The tick runs due segment runs before the due enrollments, so new enrollments start in the same tick. The scheduled tick and the tenant tick (tools, tests) both do it; the tenant filter of migration 123 applies.
  8. **API** (`/api/engage/segments`): tenant users list, read, preview a definition and count a stored version (count and a sample of at most 100, nothing stored); tenant admins create segments and publish versions. `GET /api/engage/journeys/:id/segment-runs` lists a journey's runs. The UI is the Segments section of the Lucy page (WP-20, ADR-015).
- **Not in v1:** product-level order history (what was bought: `product_ids` are stored but not queryable), segments over events other than orders, segment-entry triggers fired by a change (a customer entering the segment), SMS and WhatsApp consent, saved counts over time, a "dry run" of a journey.
- **Consequences:** + audiences are reproducible and auditable (versions, slots, run rows, counts); + a scheduled run cannot double-enroll or silently re-target; + the same semantics in SQL and in the journey evaluator is tested, not assumed. − evaluating a segment scans the tenant's order events once per run and per count (fine for the pilot's tens of thousands of customers; a materialized per-customer order summary is the next step if a tenant outgrows it); − a run that was interrupted waits ten minutes before another worker takes it over; − string comparison with `gt/lt` uses byte order (C collation), which differs from a locale's order for some non-ASCII text.
