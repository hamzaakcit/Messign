# ADR-012: The journey executor keeps its state in Postgres and acts once per step; pg-boss only wakes it up

- **Status:** Accepted (2026-11-09, WP-16; extended by WP-17)
- **Context:** Journeys (ADR-011) must start from events (WP-08 writes a `trigger_outbox` row in the same transaction as the event) and from the trigger API, wait (delay, wait-until with timeout) and stop when an exit event arrives, for example an order after an abandoned cart. Jobs retry, workers crash, two instances run at once and events arrive out of order, and once message steps exist (WP-17) every repeated step is a duplicate message to a real customer. pg-boss (ADR-003) runs on its own connection: it cannot share a transaction with engage writes, and the engage role has no grants on its schema.
- **Decision:**
  1. **The database is the truth; pg-boss is a wake-up.** `engage.enrollments` holds one row per profile in a journey (version, current step, `next_run_at`, end status and reason); `engage.enrollment_steps` holds one row per step per enrollment (started, wake time or deadline, outcome, next step). Migration `121_engage_enrollments.sql`. A pg-boss job (`engage/journey-tick`) runs every minute, and ingestion and the trigger API ask for one at once; the tick finds its work in the database, so a lost, late or doubled wake-up changes latency, never behaviour.
  2. **Once per step.** Every action runs in one tenant transaction that holds the enrollment's row lock (`FOR UPDATE SKIP LOCKED`). Before a step acts, its ledger row is read: a finished step is never run again. The ledger has one row per (enrollment, step) and the database refuses changes to a finished step, to an ended enrollment and to an enrollment's identity; the engage role cannot delete either. A crash rolls back to the last committed state, and the retry does the work once. WP-17 message steps will take their idempotency key from (enrollment, step), so the message ledger dedupes a send as well.
  3. **Enroll once.** An enrollment is unique per (journey, trigger key): the event id for event triggers, the caller's idempotency key for API triggers. A profile has at most one active enrollment per journey (partial unique index). The trigger API stores a hash of the request: the same request again returns the same enrollment (`duplicate`), the same key with a different profile or payload is a 409.
  4. **Exits by time, not arrival order.** Before every run, exit conditions are checked against the profile's stored events that occurred at or after the trigger (the trigger event itself excluded). An order that arrives before the cart event it follows still ends the enrollment. Any event for a profile wakes its running enrollments at once, so an exit or a wait-until match does not wait for the delay to end.
  5. **Timing.** The first step counts from when the trigger happened (a one-hour delay after a cart event is one hour after the cart changed); later steps count from when the previous one finished. Wait-until matches events between the step's start and its deadline. Events more than 24 hours old are stored but start nothing, so a backfill of history cannot enroll everyone.
  6. **Finding work across tenants.** The tick has no tenant. Two SECURITY DEFINER functions, `engage.pending_trigger_work(limit)` and `engage.due_enrollment_work(limit, now)`, return tenant and row ids only; each piece of work then runs in its own `withEngageTenant` transaction. The isolation suite lists every definer function the engage role can call, so a new one fails the suite until it is reviewed and added.
  7. **Versions.** An enrollment stays on the version it started on when a newer version is activated. Stopping the journey (no active version) ends running enrollments as `exited / journey_stopped`.
  8. **Branch, message, re-entry, holdout (WP-17, migration `122_engage_journey_messages.sql`).**
     - *Branch:* branches are tried in order on the profile's attributes and the enrollment's payload; the first match wins, otherwise the fallback. The ledger records which.
     - *Message:* the step creates the message from the template **in the same transaction** as the step (`createTemplatedMessageOn`), with idempotency key `journey:<enrollment>:<step>` and the step's `message_id`; a step and its message exist together or not at all. The account is the tenant's one active email account; with none or several the enrollment fails (`no_email_account`, `email_account_ambiguous`) rather than guess. A pinned `template_version` is honoured; otherwise the latest version at the time of the step.
     - *Sending:* the same tick then runs the dispatcher (`dispatchDueAcrossTenants`): due queued messages of every tenant (a third id-only definer function, `engage.due_message_work`), each dispatched in its tenant through the send gate. With `SEND_MODE` off it reads nothing; tenant `send_enabled`, consent, suppression, allowlist (sandbox), quiet hours, caps and budget apply as for any message.
     - *Re-entry:* `never` (default): a profile enters a journey once, ever; `after_exit`: again once its previous enrollment has ended. Never two active enrollments of one journey for one profile. Checked under a lock per (journey, profile).
     - *Holdout (D-11):* `holdout_percent` (0–50, default 10) in the definition; the cohort is drawn once at enrollment and is part of the enrollment's identity (the database refuses a change). A holdout enrollment runs every step; its message steps are recorded as `held_out` and create no message, so WP-21 can compare treatment and holdout.
     - Date-attribute triggers remain WP-25.
  9. **Cart abandonment and the simulator (WP-18).**
     - *The journey:* `engage/journeys/cartAbandonment.ts` is the first ready-made journey: cart_updated → 1 h → reminder 1 → 24 h → reminder 2 → end; an order (by when it happened) ends it; re-entry after exit; 10% holdout. `installCartAbandonment` creates the two templates and a **draft** journey; a tenant admin still approves and activates it.
     - *Tenant tick:* `runTenantTick(org, now)` runs one tenant's outbox and due enrollments inside that tenant only, on a caller's clock, and throws instead of deferring. Tools use it; the scheduled tick never takes a caller's clock, so a simulation cannot move another tenant's time.
     - *Work-list filter (migration `123_engage_work_list_filters.sql`):* the three id-only work lists take an optional list of tenants (NULL = all, what the scheduled tick passes). Found by the simulator: a test that ran the global tick on its own clock acted on the simulation tenant's enrollments. In production there is one clock, so this was a test hazard, but anything that drives the tick on its own clock must now name its tenants (`runJourneyTick({ onlyOrganizations })`, `dispatchDueAcrossTenants({ onlyOrganizations })`).
     - *Simulator:* `engage/simulator/cartSimulator.ts` (pure, seeded) plans customers, cart and order events, repeats, duplicate deliveries, late reports and missing consent, and derives each customer's expected outcome from the scenario alone. `runCartSimulation` feeds the plan through the real ingestion path, the tenant tick and the dispatcher; `verifyCartSimulation` compares the database with the expectation. Operator script: `npm run engage:simulate-carts` (mock accounts only when dispatching, sandbox forced).
     - *Out of scope:* events that arrive after a step acted cannot undo it. The simulator's late order sends reminder 1 because the order was not yet known: that is the honest expectation, not a defect.
- **Consequences:** + retries, crashes, concurrent workers and replayed triggers cannot repeat a step; + an exit is honoured whatever order events arrive in. − latency up to one minute when a wake-up is lost; − an event recorded late (after a step already acted) cannot undo that step; − the scheduler's two definer functions are a reviewed exception to "no cross-tenant reads".
